# Contributing to Eazy Review

Eazy Review is a maintainer-led independent project. Contributions are welcome
when they fit the current scope and can be reviewed with clear evidence.
Please follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Propose a focused change

Check existing issues and the [task ledger](docs/TASKS.md) before opening a
bug report or feature proposal. Describe the problem, affected journey and
smallest useful outcome. Discuss substantial features or design changes with
the maintainer before implementation; [BLUEBOOK](docs/BLUEBOOK.md) owns scope
and [DESIGN](docs/DESIGN.md) owns the UI.

For questions, see [Support](SUPPORT.md). Disclose vulnerabilities through
the [security policy](docs/SECURITY.md), never a public issue.

## Develop and verify

Follow the [development guide](docs/DEVELOPMENT.md) and
[install rules](docs/SECURITY.md#install-and-setup-scripts). Use local Supabase
for development. Keep credentials and personal data out of commits, logs and
screenshots. Coding agents must also follow [AGENTS.md](AGENTS.md).

Keep your change focused and preserve unrelated work. Use the
[validation map](docs/AGENT_WORKFLOW.md#validation) after reviewing executable
inputs. Include actual results and checks you could not run; web evidence
does not establish native or physical-device acceptance.

## Open a pull request

Use the [pull request template](.github/pull_request_template.md). Explain the
problem, resulting behavior, validation and material limitations. Include
screenshots with platform and environment context for visible changes.
Update affected documentation under the [documentation policy](docs/DOCUMENTATION_POLICY.md)
and keep the template's documentation and Project #4 fields.

The maintainer coordinates scope, review, acceptance and board updates.
Local checks, human acceptance, merge and deployment are separate steps.
Contributing does not imply a response-time or release commitment.
